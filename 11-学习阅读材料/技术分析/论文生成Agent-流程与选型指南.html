论文生成 Agent：开发流程与选型指南

输入用户的项目源码 + 论文题目 + 格式要求，输出一篇符合真实项目和格式要求的论文。本文讲清楚：这个项目分几步、每步干嘛、每步有哪些做法可选。每一步你可以点选一个方案，页面底部实时汇总你的选型，复制后可直接用于团队对齐。

心智模型 流程总览 ① 摄取 ② 知识构建 ③ 格式规格化 ④ 规划 ⑤ 生成 ⑥ 校验 ⑦ 渲染 贯穿三件事 决策清单 术语表

先建立一个心智模型

不搞懂这个，后面所有技术名词都是零散的。懂了它，每个步骤你都能看出"这在解决四件事里的哪一件"。

大模型 API = 一个远程函数 f(提示词) → 文本  ·  无状态（每次调用互不记得）· 按字收费（token 计费）· 结果不确定（同输入可能不同输出）

正因为它有这三个特性，整个 agent 技术栈本质上只是在做四件事：

1 · 上下文工程每次调用往提示词里塞什么材料。质量的上限由它决定。落到步骤 ①②④⑤
2 · 输出约束逼它稳定输出你要的结构，而不是一段靠碰运气解析的自由文本。落到步骤 ③⑤
3 · 结果校验怎么发现它这次有没有胡说。它的错误是"看起来对、实际错"。落到步骤 ⑥
4 · 编排迭代把单次调用串成流水线，并可持续改进。落到贯穿三件事

流程总览：7 步

点击任意节点跳到对应步骤。1、2 步决定"内容真不真"（这是产品的生死线），3、7 步决定"格式对不对"。

1

仓库摄取

把用户上传的代码变成"干净、可分析"的输入

干嘛的：接收上传的仓库，扔掉干扰物（依赖包 node_modules、venv、构建产物、锁文件），摸清项目构成——什么语言、多大规模、有没有 README 和 git 历史。

不做这步，垃圾内容会按字收费地稀释模型注意力——成本翻倍，质量反而下降。
A已选

自维护规则清单

自己写一份忽略目录/文件清单，按规则过滤。

适合起步阶段，白盒可控、好排查
工作量小
坑长尾目录名、中文路径、压缩包嵌套
B已选

用现成打包工具

repomix / gitingest 等开源工具，自带去噪和合并输出。

适合零开发快速验证需求
工作量极小
坑黑盒、可控性弱，输出格式未必匹配你的后续管线
C已选

语言自适应过滤

识别项目语言和框架，精确排除无关物。

适合中后期，规则长尾积累多了再上
工作量中
坑本质是规则引擎，需要持续维护
B 起步（一周内能跑通）→ 用户量起来后切 A/C 自建。安全红线：用户代码只做静态解析，永不执行。
2

知识构建 ← 整个项目投入最重的一步

把"代码"变成模型写作时能引用的"材料"

干嘛的：产出一份关于这个项目的"材料库"。你在网上看到的 RAG、向量库、embedding，全是这一步的工具。写作质量的上限完全由这步决定——这也是各家同类产品拉开差距的地方。

模型不认识你的用户。它写得出多"贴合真实项目"，取决于你喂了什么材料、喂得多准。
A已选

全量直塞上下文

去噪后整个仓库直接放进提示词。学生项目通常塞得下（几十万字符 ≈ 几万 token）。

适合MVP 首选，一周能做出来，检索质量不用操心
工作量极小
坑仓库超限则成本飙升；无逐条溯源粒度
B已选

向量检索（经典 RAG）

代码切块 → 向量化 → 存向量库 → 写作时按需检索相关片段。

适合仓库大到塞不下的场景
工作量中
坑代码切块比文本难（不能从函数中间切断），切块质量决定成败，检索不准全盘皆输
C已选

结构化蒸馏（效果天花板）

先静态解析（语法树 AST、模块依赖、git 提交历史），再用便宜模型把材料提炼成一条条"事实卡片"入库，每条注明出自哪个文件。

适合追求"内容真、可审计"的核心路线
工作量大
坑管线最长；抽取器要按语言栈分别适配
A 起步验证 → 渐进演进到 C（git 历史能挖出"遇到问题→改方案→指标提升"的叙事，这是论文最有价值、也最难伪造的原料）；B 视仓库大小决定要不要补。
3

格式规格化

把"格式要求"变成机器可校验的规则对象

干嘛的：产出一份 FormatSpec——标题分几级、图表怎么编号、参考文献什么格式……后续渲染照它执行、校验照它检查。

格式如果每次让模型"现场发挥"，永远不稳定；规则化之后才能用脚本 100% 检查，而不是靠人眼。
A已选

用户填结构化表单

让用户按表单勾选/填写格式规则。

适合积累规则库的种子阶段
工作量小
坑用户嫌麻烦、覆盖不全，容易流失
B已选

解析 Word 样本

docx 本质是 zip + XML，用现成库读样式定义和真实文档结构，自动抽出规则。

适合主路线——用户上传学校模板即可
工作量中
坑学校模板很脏，规则长尾多，需要容错
C已选

LLM 翻译自然语言

用户写一段"我们学校要求……"，模型翻译成规则对象。

适合兜底，覆盖前两者搞不定的场景
工作量小
坑模型幻觉会混进规则库，必须加校验层
B 为主、C 兜底；高频规范（如 GB/T 7714 参考文献格式）内置成确定性规则库，三种方式都不用碰它。
4

规划

拆大纲成任务树：几章、每章写什么、调用哪些材料

干嘛的：先生成章节树（结合论文题目 + 材料库 + FormatSpec 的结构要求），再给每个叶子节点分配：写作目标、所需材料子集、目标字数。

一口气生成全文，模型必然"写到后面忘了前面"。规划是把长文拆成模型能力范围内的独立调用。
A已选

一次生成全文

单次调用直接产出整篇。

适合只适合短文 / 单章
工作量极小
坑长论文必然前后失忆、术语漂移
B已选

先大纲、后逐章（map-reduce）

两阶段：第一次调用产出大纲；然后逐章独立调用，每章带自己的上下文 + 全局术语表。

适合长文的标准解，业内主流
工作量中
坑需要额外维护"全局一致性"（见贯穿事项）
C已选

多 agent 协作

规划师、作者、编辑等多个角色 agent 反复磋商。

适合追求上限的中后期
工作量大
坑复杂度高、成本高、难调试，MVP 明确不需要
B 是默认答案。全局一致性别指望模型记住——用数据库表（术语表/符号表/数字表）解决，每章生成时注入、校验时核对。
5

生成

带约束地写初稿。这一步内部有 3 个独立决策点

干嘛的：逐章产出初稿。三个子决策：①上下文组装（给什么材料——大纲节点 + 该章材料 + 全局术语表，这是质量核心，比提示词措辞重要得多）；②输出约束（怎么拿回结构化结果）；③模型分工（贵的写正文、便宜的干杂活，成本差一个量级）。

A已选

自由文本输出

模型返回一段文章，程序自己解析。

适合原型验证
坑结构解析靠碰运气，脏数据直接进下游
B已选

JSON 结构化输出

用各家 API 的 schema 模式强制输出 JSON，字段、类型、枚举全部约束死。

适合主流做法，下游处理稳定可靠
坑超长正文塞 JSON 里偶发截断，要按章拆分
C已选

结构化 + 内嵌引用标记

在 B 的基础上，要求事实性句子自带材料引用编号，终稿剥离标记、留档备查。

适合"内容真"的核心保障，与第⑥步联动
坑模型偶尔忘标或标错，需要校验兜底
模型分工是另一个必答题：旗舰模型写正文，便宜模型承担蒸馏和校验等 token 大头环节——这是控制单篇成本的关键杠杆。
6

校验

生成 ≠ 可交付。挑错、分流：能修的打回重写，材料缺的进待补清单

干嘛的：分可靠性地查三类问题——格式合规、事实有据、前后一致。这三类分别用不同手段查，能用脚本查的绝不劳烦模型。

A已选

确定性脚本（可靠性 100%）

格式规则、编号、引用格式、数字跨章一致——渲染后重新解析逐项比对，纯代码零模型。

适合一切能写规则的检查
坑规则覆盖有长尾，需要持续积累
B已选

LLM-as-judge（语义评审）

拿另一个模型按检查清单逐条评审："这句话有没有材料依据"。

适合脚本报不了"内容真假"的语义检查
坑有误报——宁可错杀打回重写，也不放过编造
C已选

人工抽检

上线初期人工看一批产出，标注问题反哺规则库和检查清单。

适合冷启动阶段必做，顺便积累评估集
坑不可规模化，定位是过渡手段
A + B 组合是常态，C 在冷启动期并行。回改循环要设最大轮数（如 3 轮），防止"打回→重写→又不过"死循环烧 token。
7

渲染

结构化内容 → 最终 Word，确定性执行

干嘛的：按 FormatSpec 把结构化内容填进 Word 模板。这一步的目标是"零模型参与排版"。

✗已选

让 LLM 直接吐格式

让模型连排版一起生成。

坑不可行——排版必乱，返工无底洞。列在这里是防止团队踩坑
A已选

模板引擎（docxtpl）

学校样本改造成模板（Word 版的"填空模板"），程序往里填内容，样式天然继承学校要求。

适合主流做法
工作量中
坑模板本身要按学校积累，前期限 1-2 个学校做深
B已选

直接操作 docx XML

程序级完全控制 Word 文档对象。

适合疑难格式（如公式 OMML）才需要
坑工作量大、细节地狱，非必要不上
A 为主，遇到模板引擎搞不定的个别格式再局部用 B。图表（架构图、数据图）由程序自动生成后作为图片插入，同样不让模型画。

贯穿全程的三件事

不属于哪一步，但从第一天就要立项。它们决定项目能不能持续迭代，而不是"能跑一次的 demo"。

编排：把步骤串起来跑

生成是分钟级长任务，必须异步化。

线性脚本
MVP 够用状态机+队列
生产必需agent 框架
可选，非必需

LangGraph 这类框架把循环抽象成图，省原型时间，但调试成本高。它不在关键路径上——你的核心壁垒不在框架里。

可观测：LLM 应用的日志

每次模型调用记录：输入、输出、花费、耗时、版本。

自建日志表
起步够用Langfuse 等
开箱即用全链路追踪
规模化需要

比传统日志重要得多——因为 LLM 的错误是"看起来对、实际错"，没有调用记录你连错在哪一步都不知道。

评估：LLM 应用的单元测试

攒一批"真实仓库 → 真实论文"配对当回归测试集。

10 对起步改动必跑回归指标量化对比

改一版提示词可能弄坏另外五章。没有评估集，每次改动都是盲改——这是业内公认最难、也最被忽视的一件事，第一天就该开始攒。

术语速查表

遇到没见过的词回来查。只收本文档涉及的。

术语大白话
LLM / 大模型 API现成的 AI 文字生成服务，按 token（约等于 0.7 个汉字）计费，像用水用电一样租用
prompt / 提示词发给模型的完整输入：指令 + 材料 + 格式要求
上下文窗口模型一次调用能读的最大长度上限（当前旗舰模型约 20-40 万 token）
RAG / 检索增强不让模型闭卷瞎猜，先从资料库里检索相关片段、放到提示词里让它开卷答题
embedding / 向量库把文本转成"语义坐标"，向量库按语义相似度找资料——RAG 的检索手段
AST / 语法树代码的结构化解析结果，比按行读文本可靠得多，tree-sitter 是主流解析工具
结构化输出用 API 的 schema 模式强制模型输出规定格式的 JSON，而不是一段自由文本
LLM-as-judge拿另一个模型当阅卷老师，按检查清单逐条评审产出质量
map-reduce"先拆后合"：大纲一次生成，逐章分别生成再拼起来，长文标准套路
agent 框架LangChain/LangGraph 等，帮你把模型调用、循环、状态管理封装起来的开发库
golden set / 评估集留作回归测试的"标准答案对"，每次改动用它判断质量是升是降
docxtpl / 模板引擎Word 版的"填空模板"：样式和结构做在模板里，程序只负责往里填内容
