**开讲之前，先给你一个“翻译”：agent 开发和你熟悉的软开最大的区别只有一个——** 你的核心依赖（大模型）是一个“无状态、按字收费、结果不确定”的远程函数。整个 agent 技术栈，不管名词多花哨，都是在解决四件事：**往函数里塞什么材料（上下文工程）、怎么逼它稳定输出你要的结构（输出约束）、怎么知道它这次有没有胡说（校验）、怎么把单次调用组成流水线（编排）**。记住这四件事，下面每一步你都能对号入座。
下面逐步骤讲：这步干嘛的、为什么必须有、业内的可选项各是什么。

## ① 仓库摄取

**干嘛的**：接收用户上传的代码，扔掉干扰物（依赖包、构建产物、锁文件），摸清项目构成（什么语言、多少文件、有没有文档和 git 历史）。
**为什么必须有**：不做这步，垃圾内容会按字收费地稀释模型注意力，成本翻倍、质量下降。
**可选项**：A. 自己写去噪规则清单（可控、费人工）；B. 用现成的仓库打包工具（如 repomix / gitingest 这类开源项目，自带去噪，起步够用）；C. 按语言自适应的智能过滤（后期优化项）。

## ② 知识构建（整个项目投入最重的一步）

**干嘛的**：把“代码”变成模型写作时能引用的“材料”。你在网上看到的 RAG、embedding、向量库，全都是这一步的工具。
**为什么必须有**：模型不认识你的用户，写作质量的上限完全取决于你喂给它什么材料。
**可选项**（按复杂度排）：
- **A. 全量直塞**：去噪后整个仓库直接放进上下文。学生项目通常塞得下。最简单，一周能做出来。
- **B. 向量检索（经典 RAG）**：代码切块 → 转成向量 → 存向量库 → 写作时按需检索相关片段。仓库大才需要；代码切块比文本切块难（不能从函数中间切断），切块质量决定成败。
- **C. 结构化蒸馏**：先做静态解析（语法树、模块依赖、git 提交历史），再用便宜模型把材料提炼成一条条“事实卡片”入库。最贵，但效果天花板，也是各家同类产品的真正差异点。
- **业内常见路径**：从 A 起步验证需求，逐步演进到 C；B 看仓库大小决定要不要加。

## ③ 格式规格化

**干嘛的**：把“格式要求”变成一份机器可校验的规则对象（标题层级、图表编号方式、参考文献格式……），后续渲染和校验都用它。
**为什么必须有**：格式如果每次让模型“现场发挥”，永远不稳定；规则化之后才能用脚本 100% 检查。
**可选项**：A. 用户填结构化表单（确定性强、用户嫌麻烦）；B. 解析 Word 样本（docx 本质是 zip+XML，有现成库读样式定义，自动但学校模板很脏）；C. LLM 把用户一段话翻译成规则对象（省事、需二次校验）。业内通常是 B 为主、C 兜底、高频规范（如 GB/T 7714）内置成规则库。

## ④ 规划

**干嘛的**：拆论文大纲成任务树——几章、每章写什么、调用哪些材料。
**为什么必须有**：一口气生成全文，模型必然“写到后面忘了前面”。
**可选项**：A. 一次生成全文（只适合短文）；B. 两阶段“先大纲、后逐章”（每章独立调用、带独立上下文，业内叫 map-reduce 模式，长文的标准解）；C. 多 agent 协作（规划师/作者/编辑多角色，上限高、复杂度高，MVP 不需要）。

## ⑤ 生成

**干嘛的**：逐章写初稿。这一步内部有三个独立的决策点：
- **上下文组装**：每次调用给模型什么（大纲节点 + 相关材料 + 全局术语表）。这是质量的核心，比 prompt 措辞重要得多。
- **输出约束**：a) 自由文本（解析靠碰运气）；b) JSON 结构化输出（各家 API 的 schema 模式，强约束，业内主流）；c) 约定标记（比如让句子自带引用编号，写完再剥离）。
- **模型分工**：贵模型写正文，便宜模型干杂活（蒸馏、校验）。按环节分工，成本差一个量级。

## ⑥ 校验

**干嘛的**：生成 ≠ 可交付。挑错并分流：能修的打回重写，材料缺的进“待补清单”。
**可选项**（按可靠性排）：A. 确定性脚本——格式、编号、引用格式，能用脚本查的绝不劳烦模型；B. LLM-as-judge——拿另一个模型按检查清单评审（“这句话有没有材料依据”），可靠但不完美，误报可接受；C. 人工抽检——上线初期必要，顺便积累测试集。回改循环要设最大轮数，防止“打回→重写→又不过”死循环烧钱。

## ⑦ 渲染

**干嘛的**：结构化内容 → 最终 Word 文件。
**可选项**：A. 让 LLM 直接吐格式（不可行，排版必乱）；B. 模板引擎（如 docxtpl，把学校样本改造成模板、程序填空，主流做法）；C. 直接操作 docx XML（控制力最强、工作量最大，遇到公式这类疑难格式才需要）。

## 贯穿全程的三件事（不属于哪一步，但决定项目成败）

- **编排**：怎么把上面这些步骤串起来跑。选项：线性脚本（MVP 够用）→ 状态机+任务队列（生产必需，生成是分钟级长任务）→ agent 框架（LangGraph 之类，把循环抽象成图，省原型时间但调试成本高，**不是必需品**）。
- **可观测**：每次模型调用把输入/输出/花费/耗时全部记下来（自建或用 Langfuse 这类现成工具）。LLM 应用的日志比你过去做过的任何日志都重要，因为它的错误是“看起来对、实际错”。
- **评估**：攒一批“真实仓库→真实论文”配对当测试集，每次改 prompt 跑回归。这是 LLM 应用里的“单元测试”，业内公认最难、也最被忽视。
