# 首期业务流程与交互

## 当前基线 [S] 与产品方向 [C]
原项目介绍的已实现链路：登录 → 建立一个项目 → 上传资料 → 技术文档 → 逐页审阅确认 → 解锁五类 Word → 模板校验 → 逐页预览 → 修订 → 归档下载。新产品要求是在不破坏上述核心链路的情况下，进一步减少填写与确认负担。

## 核心体验规则 [C]
1. **上传即可分析**：源码/文档静态分析，不直接运行用户代码；记录成功/失败、来源文件与不确定处。
2. **简短事实确认**：展示清晰短摘要并询问“以上描述是否准确？”；可确认或有针对性修正。不抛给用户几十个必填字段。
3. **不虚构**：无法验证测试值、进度、参考文献、指导行为时，不得自造；在必要处提醒补充。
4. **两级重点**：项目级重点跨文书共用；文书级重点仅影响具体输出。当前[S]“强调生成”没有进入 Worker，作为实施 GAP。
5. **文书审阅**：用户完整逐页预览，标注修改意见，可对版本通过/不通过；预览不是下载权限。
6. **修改与历史**：基于指明的版本修订；保留可追溯历史与反馈；材料更新后提醒受影响的文书，旧版不静默更新。
7. **错误恢复**：超时、模型/转换失败可见、可安全重试；失败任务不扣共享额度。

## 简单的学生端文案
- “请上传你已经拥有的项目资料。”
- “我们整理到的项目情况如下：…… 以上描述准确吗？”
- “这份文书使用的是试点学校的已支持模板，请核对每页内容和格式。”
- “这是一份参考拟稿，不应未经审阅直接提交。”
- “已发现新资料可能影响 2 份历史文书；是否创建修订版？”（[C-规划]）

## 状态与异常
| 状态 | 页面处理 | 证据要求 |
|---|---|---|
| 待上传 | 展示明确支持类型 | 上限和文件说明 |
| 分析中 | 进度/任务状态 | job_id/trace_id |
| 待事实确认 | 用户短确认/修正 | 保留确认版本 |
| 生成中 | 异步任务状态 | 任务与模型成本 |
| 待审阅 | 全页查看，提交意见 | 文书版本 ID |
| 修订中 | 新版本，不覆盖旧版 | 源版本 ID、意见摘要 |
| 失败 | 原因分类与可重试入口 | 不误扣额度 |

## 当前范围限制
首期维持一个工作空间、一条串行完整流程，不急于开发“先选任意单页文书”的多入口模式。长期场景工作台与多项目能力要在产品验证后再展开。
