# 平台通用能力与工程复用路线

## 逻辑分层 [C-规划]
1. **统一工作空间**：账号、项目/任务、资料、事实、生成成果、历史。
2. **资料理解层**：来源分析、类型识别、静态源代码事实提取、可信度和来源。
3. **文书能力层**：已验证框架、排版规则、动态框架建议、模板解析。
4. **场景插件层**：文书组合、输入要求、任务顺序、角色与审核规则。
5. **执行与质量层**：编排、模型调用、DOCX 生成、渲染、校验、版本与导出。
6. **平台运营层**：用户、限额、权限、安全、日志、成本、配置。

## P-01 记录的现有技术 [S]
React 19 + TypeScript + Vite；FastAPI 0.162；PostgreSQL 16；Redis 7/RQ 2.1；Job/Outbox/Dispatcher/Worker；Claude Agent SDK + 百炼模型，MiMo 后备；python-docx、PyMuPDF、Windows MS Word COM；日志、会话和认证能力。版本均为项目原文日期快照，非本次依赖核验。

## 不改变的首期选择 [C]
- 保留已有本地 `thesis-doc-web` 主工程，不重复创建新系统。
- 暂不拆微服务、Kubernetes、多租户插件市场。
- 第一批目标：中国大陆云 Linux、单机容器化的可行性验证；资源配置依据实测，不承诺 2 核 4G 必然足够。
- **重要阻断**：Windows COM 的逐页渲染需要替换/重新验证可用于服务器端的方案（见第 06 模块）。

## 演进解耦序列 [R]
1. 保留原功能，对照真实官方模板构建回归集。
2. 把“事实提取”从具体文书 Skill 的模板知识中分离，形成稳定的信息资产契约。
3. 文书结构、排版样式和规范规则分别表达，允许场景/模板覆盖。
4. DOCX 渲染/校验服务形成版本可测的内部接口，避免与业务逻辑相互锁死。
5. 先用一类非毕设文书验证复用；若质量和成本可接受，再开放框架动态生成。
6. 场景插件先使用**声明式配置**；不允许用户上传任意代码在 Worker 执行。

## 避免过度架构
一个应用内部的清晰模块优先于独立部署的复杂服务；只有当吞吐、安全隔离或团队规模等可测需求出现才考虑拆分。
